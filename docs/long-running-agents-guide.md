## 1. はじめに

### 1.1 この記事の目的

AI エージェントが**複数のコンテキストウィンドウにわたって進捗を維持する方法**について解説する。長時間かかるタスク（大規模なソフトウェア開発など）を AI エージェントに任せる際の課題と、その解決策を提示している。

### 1.2 用語解説

| 用語 | 説明 |
|------|------|
| **長時間実行エージェント** | 1回のセッションでは完了しない、複数セッションにまたがるタスクを実行する AI エージェント |
| **コンテキストウィンドウ** | AI が一度に処理できる情報量の上限。会話が長くなると古い情報から忘れていく |
| **セッション** | エージェントとの1回のやり取り。セッションが終わると、エージェントはメモリをリセットする |
| **MCP (Model Context Protocol)** | AI エージェントが外部ツール（ブラウザ、ファイル操作など）と連携するための標準プロトコル |
| **ハーネス** | エージェントを制御・支援するための仕組み。セットアップ、進捗管理、テストなどを含む |
| **End-to-end テスト** | システム全体を実際に動かして行うテスト。ユーザーと同じ操作でテストする |

### 1.3 なぜこの問題が重要なのか

AI エージェントは強力だが、以下の制約がある：

1. **メモリの非永続性**: 新しいセッションが始まると、前のセッションの内容を覚えていない
2. **コンテキストの枯渇**: 長い作業をすると、途中で情報が溢れて最初の方を忘れる
3. **進捗の喪失**: セッションをまたぐと、何をどこまでやったか分からなくなる

これらを解決しないと、大規模なタスクを AI に任せることができない。

## 2. 課題：なぜ長時間実行は難しいのか

### 2.1 根本的な問題

> 「エージェントは離散的なセッションで動作し、新しいセッションごとに前のセッションのメモリがない」

つまり、AI エージェントは「1日働いて、翌日には昨日のことを何も覚えていない」状態で毎回スタートする。

### 2.2 4つの失敗パターン

長時間実行エージェントで頻繁に発生する問題を4つに分類：

| # | 失敗パターン | 説明 | 具体例 |
|---|-------------|------|--------|
| 1 | **過度な計画** | 一度に多すぎることを試み、コンテキストが枯渇する | 200機能を一気に実装しようとして、途中で何をしていたか分からなくなる |
| 2 | **早期の完了宣言** | 部分的な進捗を見て、プロジェクト全体が完了したと判断する | 1機能が動いただけで「全て完了しました」と報告してしまう |
| 3 | **機能の早期完了マーク** | テストせずに「できた」とマークする | コードを書いただけで動作確認せずに次へ進む |
| 4 | **環境セットアップに時間を浪費** | 毎セッション、開発環境の構築からやり直す | 毎回「このプロジェクトはどうやって動かすんだっけ？」から始まる |

## 3. 解決策：二部構成アプローチ

Anthropic が提案する解決策は、**2種類のエージェントに役割を分担**させること。

### 3.1 Initializer Agent（初期化エージェント）

プロジェクト開始時に一度だけ実行するエージェント。**土台を作る役割**。

#### 責務

1. プロジェクト全体を理解し、必要な機能をリストアップする
2. 開発環境を構築し、起動方法を記録する
3. 進捗管理の仕組みを整える

#### 作成する3つの成果物

| 成果物 | 説明 |
|--------|------|
| **features.json** | 200以上の具体的な機能をリスト化したファイル。最初は全て「未完了」 |
| **init.sh** | 開発サーバーを起動できる初期化スクリプト |
| **claude-progress.txt** | エージェントの作業履歴を記録するファイル |

さらに、初期 Git コミットも行う。

### 3.2 Coding Agent（コーディングエージェント）

実際の開発を行うエージェント。**毎セッション実行される**。

#### 責務

1. 前回の進捗を確認する
2. **1つの機能だけ**に集中して実装する
3. テストで動作確認する
4. 完了したらマークし、進捗を記録する
5. Git コミットして終了する

#### 重要な原則

- **一度に1機能のみ**：複数機能を同時に手がけない
- **必ずテスト**：コードを書くだけでなく、動作確認してから完了とする
- **進捗を記録**：次のセッションの自分（または別のエージェント）に引き継ぐ

## 4. 実装パターン詳細

### 4.1 features.json（機能リスト）

#### 目的

- プロジェクトの全体像を明確にする
- 進捗状況を追跡する
- エージェントが「次に何をすべきか」を判断できるようにする

#### JSON 構造

```json
{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}
```

#### 各フィールドの説明

| フィールド | 型 | 説明 |
|-----------|-----|------|
| `category` | string | 機能の分類（functional, ui, performance など） |
| `description` | string | 機能の簡潔な説明（何ができるようになるか） |
| `steps` | array | テスト手順。人間が見ても分かるステップバイステップの手順 |
| `passes` | boolean | `false` = 未完了、`true` = 完了（テスト済み） |

#### ポイント

- **200以上の機能**を定義する（細かく分割する）
- 最初は**全て `passes: false`** で始める
- 機能は**削除・編集しない**（passes フィールドのみ変更可）
- 各機能は**End-to-end テスト**として定義する（コードの単位ではなく、ユーザー操作の単位）

### 4.2 init.sh（初期化スクリプト）

#### 目的

- 開発環境のセットアップを自動化する
- 毎セッション、同じ手順で環境を構築できるようにする
- 「どうやって動かすんだっけ？」という時間の浪費を防ぐ

#### 含めるべき内容

```bash
#!/bin/bash

# 依存関係のインストール
npm install

# 環境変数の設定
export DATABASE_URL="..."

# 開発サーバーの起動
npm run dev
```

#### ポイント

- **実行可能**であること（`chmod +x init.sh`）
- エラーが出たら分かるようにする
- 必要に応じてヘルスチェックを含める

### 4.3 進捗ファイル（claude-progress.txt）

#### 目的

- セッション間で情報を引き継ぐ
- 「前回どこまでやったか」を記録する
- 次のエージェントへの申し送り

#### 記録すべき内容

- 今回実装した機能
- 発生した問題とその解決方法
- 次回やるべきこと
- 注意点・ハマりポイント

#### 例

```
## 2024-01-15 セッション

### 完了した機能
- feature-001: ログインボタンの実装

### 発生した問題
- CORSエラーが発生 → バックエンドの設定を修正で解決

### 次回やること
- feature-002: ログアウト機能の実装

### 注意点
- APIのエンドポイントが /api/v2 に変更されている
```

## 5. セッション管理

### 5.1 セッション開始時の手順

エージェントは毎セッション、以下の手順で始める：

```
1. pwd                           # 作業ディレクトリを確認
2. cat claude-progress.txt       # 前回の進捗を読む
3. cat features.json             # 機能リストを確認
4. git log --oneline -20         # 最近のコミットを確認
5. ./init.sh                     # 開発サーバーを起動
6. （基本機能の検証テスト）        # 既存機能が壊れていないか確認
```

#### 実際のセッション例

```
[Assistant] I'll start by getting my bearings...
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log...
[Tool Use] <bash - git log --oneline -20>
```

#### なぜこの順序か

1. **ディレクトリ確認**: 間違った場所で作業しないため
2. **進捗確認**: 前回の続きから始めるため
3. **機能リスト**: 次に何をすべきか判断するため
4. **Git ログ**: 最近の変更を把握するため
5. **サーバー起動**: テストできる状態にするため
6. **検証テスト**: デグレ（退行）がないことを確認するため

### 5.2 セッション終了時の手順

セッション終了前に必ず行うこと：

```
1. features.json を更新       # 完了した機能の passes を true に
2. claude-progress.txt を更新  # 今回の作業内容を追記
3. git add && git commit       # 変更をコミット
```

#### ポイント

- **テストが通る状態でのみコミット**する
- 次のセッションで分かるように、進捗ファイルに詳細を記載する
- コミットメッセージは分かりやすく書く

## 6. テスト戦略

### 6.1 End-to-end テストの重要性

なぜ End-to-end テストが重要か：

> 「エージェントはコード単独では明らかでないバグを識別できた」

- コードを見ただけでは分からないバグがある
- **実際に動かして確認**することで、ユーザーが遭遇するバグを発見できる
- 機能を「完了」とマークする前に、必ずテストする

### 6.2 Puppeteer MCP の活用

**Puppeteer** は、ブラウザを自動操作するツール。MCP サーバーとして利用することで、エージェントがブラウザ操作を行える。

#### できること

- ページへのナビゲーション
- ボタンのクリック
- フォームへの入力
- スクリーンショットの撮影と確認
- 要素の存在確認

#### テストの例（Claude.ai クローンの場合）

```
1. メインインターフェースにアクセス
2. "New Chat" ボタンをクリック
3. 新しい会話が作成されたことを確認
4. チャットエリアがウェルカム状態を表示していることを確認
5. サイドバーに会話が表示されていることを確認
```

### 6.3 「人間と同じ方法でテスト」の考え方

- **ユーザー視点**でテストする
- 内部実装ではなく、**画面で見える結果**を確認する
- 実際のブラウザを使い、実際のクリックを行う

### 6.4 制限事項

Puppeteer MCP には制限もある：

- **ブラウザネイティブのアラートモーダル**を認識できない
- JavaScript の `alert()` や `confirm()` は検出が難しい
- そのため、カスタムモーダルを使う設計が推奨される

## 7. Git による進捗管理

### 7.1 なぜ Git を使うか

- **履歴が残る**: 何をいつ変更したか追跡できる
- **復旧できる**: 壊れたコードを前の状態に戻せる
- **セッション間の橋渡し**: コミット履歴を見れば、前回の作業が分かる

### 7.2 コミットメッセージの書き方

分かりやすいコミットメッセージを書く：

```
# 良い例
feat: 新規チャットボタンの実装
fix: サイドバーの表示バグを修正
refactor: API呼び出しを共通関数に抽出

# 悪い例
update
fix bug
WIP
```

### 7.3 不良コードからの復旧

エージェントがバグを入れてしまった場合：

```bash
# 直前のコミットを確認
git log --oneline -5

# 問題のあるコミット以前に戻す
git reset --hard <commit-hash>
```

Git があることで、失敗を恐れずに実験できる。

## 8. 失敗パターンと対策（まとめ表）

| 問題 | Initializer Agent の対策 | Coding Agent の対策 |
|------|--------------------------|---------------------|
| **プロジェクトを早期に完了宣言してしまう** | 全要件を網羅した包括的な機能リストを作成 | 機能リストを読み、1つずつ着実に実装 |
| **バグのある進捗が記録されない** | 初期 Git リポジトリと進捗ノートを作成 | セッション開始時に進捗を確認、終了時にコミット |
| **機能を早期に完了マークしてしまう** | テスト手順を含む機能リストを作成 | テストで自己検証してから完了マーク |
| **アプリのセットアップに時間を浪費** | 実行可能な `init.sh` を作成 | セッション開始時に `init.sh` を読んで実行 |

## 9. 今後の展望

### 9.1 スペシャライズドエージェント群

記事では、将来的に**専門化されたエージェント群**が有効である可能性を示唆している：

| エージェント | 役割 |
|-------------|------|
| **テストエージェント** | 機能のテストに特化 |
| **QAエージェント** | 品質保証、バグ発見に特化 |
| **コードクリーンアップエージェント** | リファクタリング、コード整理に特化 |

> 「単一のエージェントよりも、ソフトウェア開発ライフサイクルの各サブタスクで特化能力を発揮できる」

### 9.2 他分野への応用

このアプローチは、ソフトウェア開発以外にも応用できる：

- **科学研究**: 長期にわたる実験計画と進捗管理
- **金融モデリング**: 複雑な分析の段階的な実行
- その他、長期間にわたる複雑なタスク全般

## 10. キーポイント

この記事の最重要ポイントを7つにまとめる：

1. **メモリの非永続性が根本問題**
   - エージェントは毎セッション、記憶がリセットされる
   - 外部ファイル（features.json, 進捗ファイル）で記憶を補完する

2. **2種類のエージェントで役割分担**
   - Initializer Agent: 土台を作る（1回だけ）
   - Coding Agent: 実際の開発（毎セッション）

3. **機能リストで全体像を管理**
   - 200以上の具体的な機能を定義
   - `passes: true/false` で進捗を追跡
   - 機能は削除しない、追加のみ

4. **一度に1機能だけに集中**
   - 複数機能を同時に手がけない
   - 完了したら次へ進む

5. **必ずテストしてから完了とマーク**
   - コードを書いただけでは不十分
   - End-to-end テストで動作確認

6. **Git で進捗を記録**
   - コミットで履歴を残す
   - 壊れても復旧できる安心感

7. **セッションの開始・終了手順を固定**
   - 毎回同じ手順で始める
   - 毎回同じ手順で終わる
   - ルーティン化することで漏れを防ぐ
